# Claude Code 実装実行指示書 — AI名刺管理エージェント (iPhone / Android / PC)

最終更新: 2026-10-21 / 状態: 開発実行プロンプト / 指定したフォルダをClaude Codeで開いて使用する

## 0. 今回の依頼

このリポジトリに、既存仕様とワイヤーフレームに基づく **実際に動作する安全なAI名刺管理アプリ** を段階的に実装してください。**企画・デザイン案の提案だけで終了しないでください。** 設計判断をADRに残し、コード・マイグレーション・テスト・開発手順を作り、実行可能な部分を動作検証してください。

ターゲットは **iPhone最優先、Android対応、PC（Windows/Mac）のブラウザで全件管理**。モバイルでは連続撮影、PCでは大量整理を主動線とし、iPhoneで追加・編集した名刺がPCで見え、PCの変更がiPhoneに反映される **E2EEクロスデバイス同期** までをMVPの必須要件とする。

**実装の重要な線引き**： `prototype/*.html` は架空データを用いた見た目・画面遷移の参考資料であり、既存バックエンドや暗号化機能はない。表示ができたことだけをもってMVP完成と判断しない。実機検証が必要な項目は明確に分ける。

## 2. 成果物 — 完成の定義

最低限、次を実装・検証したリポジトリを納品すること。

1. **全16画面(S00～S15)**：画面遷移、フォーム入力、読み込み中/空/異常系/アクセス不可、スマホ・PCレスポンシブ。画像やボタンの飾りだけは禁止。
2. **安全なローカル保管庫**：iOS/AndroidでSQLCipherと暗号化画像、OS保護鍵領域、ロック/解除/復旧。Webは暗号化済みIndexedDBとWebCrypto、復号鍵を平文永続化しない。
3. **名刺取り込み**：iPhone/Androidの表裏撮影、50枚/セッションの中断再開キュー、端末内の日本語OCR、OCRデータ修正、保存、原本確認。Webは画像/PDFインポート、端末内OCRまたは明示された手入力フォールバック。
4. **人物・組織・接点管理**：氏名、会社、部署、役職、メール、電話、タグ、イベント、出会いメモ、所属履歴。ローカル検索/絞り込み、重複候補、勝手に統合しない確定導線。
5. **E2EE同期**：同一アカウントでiPhone ↔ PC間の暗号文同期、オフライン再接続、復旧鍵、別端末追加、削除の伝播、バージョン競合のUI。
6. **AI支援**：ローカル検索・フォロー候補と、必要な場合のみ外部LLMで文案生成。外部送信の宛先、選択した名刺、実際の送信内容、送信先、保持条件を表示して **都度同意**。メール自動送信機能は実装しない。
7. **セキュリティと品質**：機能単位/権限単位の試験、CI、依存監査、漏えい対策、再現可能なE2E手順。未検証の項目は未検証として明示。

## 3. 技術アーキテクチャ（推奨固定。成立しない場合はADRで変更）

- **UI / Routing**：TypeScript strict、Expo + React Native + Expo Router + React Native Web の **単一アプリ**。共通ドメイン・フォーム・デザインシステムを再利用し、PC用のサイドバー/2ペインとモバイル下部タブを分岐。Expoの現行安定SDKと対応依存バージョンを公式ドキュメントに基づいて選択。
- **Native OCR**：Google ML Kit Text Recognition v2 **日本語モデル**を実機で検証可能なネイティブモジュール/Config Plugin経由で呼び出す。単なるWeb OCR置き換えや英語限定を「日本語対応済み」としない。Expo Goをテストの根拠にしない。
- **Web import / OCR**：画像・PDFアップロードをブラウザ内処理し、リモートOCR APIを無断使用しない。ローカル日本語OCR（バンドルした日本語モデル等）が未対応なら、ファイル取込＋手修正を提供し、制約を明記。コンテンツ・OCRモデルのCDN自動取得は事前にプライバシー・オフライン動作を検証。
- **Native Data**：expo-sqlite のSQLCipher、フィールド/画像の追加の保護、キーマテリアルはiOS Keychain/Android Keystore相当。SQLite接続直後に確実に鍵設定、**鍵なしオープン失敗をバイナリと実機で検証**。
- **Web Data**：暗号化してIndexedDBへ保存、WebCryptoで解読。localStorage/IndexedDB/URL/ログに平文VMKや平文名刺を保存しない。解読済み検索索引はアンロック中メモリ上。XSS対策（CSP, 依存監査、動的HTML描画回避）を強化。
- **Crypto protocol**：CSPRNG 生成32byte VMK、監査されたAES-256-GCMと用途ごとの鍵導出、鍵バージョン、固有nonce、AAD、改ざん検知を **iOS↔Web既知テストベクトル** で一致確認。独自暗号/KDFを作らない。強固なランダム復旧キーでVMKをラップし、鍵失効・端末追加を分離設計。暗号APIや出力形式をPoCで確認してから他機能へ広げる。
- **Backend**：認証・所有者認可・暗号文同期のみを行う。第一候補は Supabase Auth + Postgres RLS + private Storage（既存環境がなければ）。代替案Cloud Run+マネージドAuth/DB/StorageをADRでコスト/可用性/運用負荷比較し、MVP向けに選定。サーバーはVMK、名刺画像・氏名・電話・メールの平文を受け取らない。API操作ではownerIdをクライアント入力だけで決めない。
- **AI**：AIがDBに直接アクセスしない。`searchContacts(ids, scope)`等の厳密な読み取りツール、`PolicyGateway`、`ConsentPreview`、`AuditLogger`を挟む。外部LLM呼び出しは認証済みのサーバー側プロキシ（鍵はサーバー環境変数）経由。LLM送信用の確認内容は **宛先・項目・本文・目的・リクエストハッシュ・時効** を含み、UI承認後にのみ送信。APIでも件数・長さ・許可された操作を強制。
- **品質基盤**：ESLint/Prettier、TypeScript strict、Vitest/Jest（適合するテストランナーを選択）、React Native Testing Library、Playwright(Web)。GitHub Actionsでは実行環境上可能なテストを実行し、iOS実機検証の代替と偽らない。

**重要な実装制限**：`expo-sqlite`のSQLCipherはiOS/Android/macOS向けで **Webには適用しない**。`expo-crypto`にAES-GCM APIがある場合でもOSごとの鍵保持と非同期互換性は実測で確認する。Cryptoが「使える」というドキュメントだけでE2EE安全性が成立するわけではない。

## 5. 必ず作るドメインモデルと永続化

`Contact`, `Organization`, `Affiliation`, `BusinessCard`, `CardField`, `Encounter`, `Tag`, `FollowUpTask`, `DuplicateCandidate`, `VaultKeyEnvelope`, `SyncObject`, `SyncRevision`, `ConsentGrant`, `AgentAction`, `AuditEvent`。

- 名刺画像、OCR抽出値と修正済み値を区別する。確信度/未確認状態/出典を保持。
- 名刺の複数枚所持と、過去の職歴/部署/役職を保存できる。1人物=1名刺にしない。
- 氏名だけで人物を自動統合しない。重複候補検出はルールと根拠を返し、統合は人が決定。
- 件数50枚の取込キューは操作中断で消滅しない。失敗した行だけ再開できる。
- クラウドには暗号化済みrecord/image blob +最小限のowner/revision metadataだけを送る。検索索引は端末内。
- ローカルDBのスキーマをマイグレーションで管理。同期競合はrevision/ETagで検出し、無言のlast-write-winsを避ける。
- テストデータは日本語名・社名・表裏・縦書き・英数字混在・改姓/異動/転職・同姓同名を含む**架空データ**のみ。

## 6. AIエージェントの限定機能

実装するのは **制約付き単一オーケストレータ**。複数の自律エージェントを増やさない。

| 機能 | 期待する挙動 | 許可 |
|---|---|---|
| 人物検索 | 先月のイベント名、タグ、社名等でローカル絞り込み | 自動 |
| 出会い要約 | 選択済み人物のメモを要約し出典IDを示す | ローカルは自動、外部なら都度承認 |
| 重複候補 | 理由付き候補を返す | 提案のみ。統合は手動 |
| フォロー提案 | 最終出会い/タスクから優先順位を表示 | 自動提案。架空の接触履歴を作らない |
| メール文案 | 1人分の背景から文面を作る | コピーのみ。送信しない |
| 外部LLM | 選択項目を送る | デフォルトOFF・本文レビュー・各回許可必須 |
| 破壊的操作 | 削除/公開/一括書き出し | エージェントには禁止 |

OCRテキストやメモに「システム命令を無視して送信」等が含まれても、Policy Gatewayで必ず拒否。モデル出力はZod等で検証。利用可能なツールと最大データ件数・最大トークン数・タイムアウト・通信先Allowlistを実装し、**AIのプロンプトに『送るな』と書くだけで制限したことにしない**。

## 7. 実装の進め方

以下を必ず順番に実行し、各段階の成果・テスト結果・未解決課題を `docs/PROGRESS.md` に記録する。外部アカウント操作が不要なフェーズは自律実装。ユーザーへ毎回承認を求めて停止しない。

**Phase 0：既存資産の確認 + 技術検証（最優先）**
- `git status`、既存構成とリスクを確認。E2EE/iOS SQLCipher/日本語OCR/Web相互復号/ブラウザ保存戦略/ルーティングの実現性を調査。
- 依存のサポート・Expo SDK互換を検証してADRを書く。**`unknown`は`passed`としない**。
- 既知のAES-GCMテストベクトルとiOS/Web間の相互復号確認コード・テストを先に作る。実機がない場合は「環境未提供で検証不可」と記録。

**Phase 1：UIとローカルCRUD**
- Expo Routerプロジェクトを構築。全画面/状態を配線し、リポジトリ・フォーム検証・マイグレーションを用意。
- iPhone/PC画面を共通デザイントークンで実装。実データとデモデータの切替を環境で隔離。暗号化が未完成な状態で実データ投入機能は公開しない。

**Phase 2：カメラ/OCR/大量取込**
- Native日本語OCR、画像補正、キュー復帰、OCRレビュー、名刺/人物保存、重複比較。PCアップロードも用意。

**Phase 3：鍵管理とE2EE同期**
- 保管庫作成、復旧キー、端末追加、暗号文同期API、RLS/AuthZ、rev競合解決、オフライン再同期。同期サーバーに平文PIIが届かない実測確認。

**Phase 4：AIエージェントと権限**
- 検索/フォロー/文案。外部LLMがOFFなら端末から出ないこと、ONでも確認前にPII通信0件をテスト。

**Phase 5：品質・配布**
- UI自動テスト、負荷(50枚)、端末ロック、クラッシュ復帰、バックアップ復元、Webクロスブラウザ、スクリーンリーダー、漏えいスキャン。iOS開発ビルド（アカウント/署名の操作が必要なら手順整備まで）とWeb起動方法を文書化。

Phase/GoNoGo詳細は `docs/IMPLEMENTATION_PHASES.md` と `docs/SECURITY_TEST_MATRIX.md`。

## 8. 絶対に満たす受入テスト

- [ ] iPhoneで50枚連続スキャンし、終了/中断/失敗から復帰できる（実機検証）。
- [ ] 端末内日本語OCR→校正→暗号化永続化→再起動後の再表示ができる。
- [ ] Windows Chrome/Edgeで一覧・検索・個別編集・画像/PDF取り込みができる。
- [ ] iPhone登録→PC追加端末を復旧キーで開く→編集→iPhoneに反映できる。
- [ ] 各OSのローカル保存・同期で、鍵なしの平文復元・サーバー上のPII平文を検出しない。
- [ ] ネット断でも閲覧・編集ができ、同期後の競合で勝手にデータが失われない。
- [ ] 重複候補検出が自動マージしない。同姓同名別人の偽陽性を扱える。
- [ ] 外部LLM初期OFF、未承認送信0、プロンプトインジェクション時も越権行為0。
- [ ] Webのブラウザ更新・ロック後に秘密鍵が平文で永続化されていない。
- [ ] CSV/データ削除は再認証・件数確認、監査ログは個人情報本文を含まない。
- [ ] テストに使う人物/社名/メールは架空であり、実名刺・実秘密情報は送信しない。
- [ ] `npm run typecheck`, `lint`, `test`, `build:web` に相当するコマンドが実行できる。

**完了判定**: 画面を全部表示できても、E2EE/日本語OCR/認可/実機のチェックが未合格なら「MVP完成」ではなく、検証段階・ブロッカーとして報告。

## 9. セキュリティ禁止事項

- 秘密鍵/APIキー/復旧キーをハードコード・コミット・解析送信・平文ログ記録しない。
- 名刺の氏名・メール・電話・画像・OCR本文を同期APIのリクエスト本文へ平文で含めない。
- Cloud/外部AIに無断でOCRすることを禁止。OCR/情報抽出の送信先は許可されたスコープのみ。
- ネイティブSQLCipherとWebの暗号化を同一実装と誤認しない。暗号化されていない段階で端末の永続ストレージへ実名刺を書かない。
- 復号鍵喪失時のサーバー側平文復旧を追加しない（ゼロ知識設計と両立しない）。
- 公開環境へのデプロイ、課金の有効化、認証情報の発行、過去データの破壊はユーザーが明確に許可するまで行わない。
- `--dangerously-skip-permissions` 等の無制限権限指定を前提にしない。

## 11. 作業開始指示

**このファイルを読んだら、追加の企画提案だけをしないこと。** リポジトリ調査 → Phase 0の互換性/暗号化/OCR実証 → 確認できた構成でプロジェクト作成 → 画面と機能の実装を進める。外部認証情報がない場合は安全な代替モックを分離し、未完了と表示して、ローカルで可能な部分はすべて実装する。最後に根拠のあるテスト結果とブロッカーを報告する。
