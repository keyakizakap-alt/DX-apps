# ANGLE Review

OpenRouterで17の専門工程を分担し、企画から振り返りまで進める日本語コンテンツ制作アプリ。HOTL（Human-on-the-loop）により通常処理は自動化し、根拠不足・取材待ち・実績待ちで停止する。

## Vercelへの反映

ソースは `DX-apps` の `main`、リポジトリ直下に配置しています。以前の `angle-review/` をRoot Directoryに指定している場合は空欄に戻してください。

1. Vercelで `keyakizakap-alt/DX-apps` をImport。Production Branchは `main`、Root Directoryは空欄（リポジトリ直下）、Framework Presetは **Other**。
2. Build Commandは `npm run build`、Output Directoryは `public`。`vercel.json` にも設定済み。画面とAI APIはFunctionで提供します。
3. 運営者がSettings → Environment Variablesに `OPENROUTER_API_KEY` を秘密情報として設定。Production / Previewの必要な環境に適用してください。利用者向けの入力欄はなく、ブラウザから送られたキーはAPIで拒否します。GitHubやフロントエンドにキーを記載しないでください。
4. 設定変更後にRedeploy。`APP_ACCESS_PASSWORD` と `SESSION_SECRET` は不要で、既存の設定も削除できます。APIキー未設定でも画面と基本チェックは利用でき、AI実行はできません。
5. 発行されたURLを開けば、そのまま利用できます。資料の分類と送信同意を確認して制作フローを開始してください。

`SITE_ORIGIN` は独自ドメインを使う場合の正確なHTTPSオリジンを指定。通常のVercel URLは `VERCEL_URL` / `VERCEL_PROJECT_PRODUCTION_URL` を検証します。旧ホスティングの `SITE_ORIGIN` を流用しないでください。`ALLOWED_MODELS` は省略時に標準の2モデル。`ALLOWED_USER_EMAILS` はSites専用です。

Vercel版はパスワードもログインCookieも使わない公開アクセスです。利用者のAI実行は運営者のOpenRouterアカウントに課金されます。OpenRouter側の支出上限とVercel側のアクセス制限・レート制限を運営者が設定してください。アプリのレート制限はインスタンス単位の共通枠（同時3件・毎分60件）であり、アカウント全体の課金上限ではありません。入力資料は利用者ごとの画面メモリで扱い、他の利用者から参照する一覧や保存機能はありません。

VercelのGitHub連携が済んでいれば、以降の `main` へのコミットが本番反映の起点になります。ビルドの成功と実際の有料AI実通信は別の確認です。

## 利用方法

「制作フロー」でテーマ・読者・目的・資料を入力し、「資料の取り扱い」で機密区分と送信同意を確認する。運営者がサーバーの `OPENROUTER_API_KEY` を設定し、キーはブラウザに送信しない。利用者はAPIキーを入力・変更できない。

企画・調査、取材設計、依頼下書き、取材素材整理、初稿、事実・引用、表記・校正、構成、リライト、最終照合、タイトル、画像指示、入稿準備、SNS文案、アーカイブ、分析を実行する。取材前でも開始でき、文字起こしを追加して再開できる。各エージェントは必要な資料を引き継いで順に実行し、失敗時は成功済み工程を保持する。モデルとAI接続は運営側で管理し、利用者向けの設定画面には表示しない。

## HOTL

検証できない根拠、最終の確認候補、要確認の原稿が残る場合は公開準備の前に停止。監督者が原稿と根拠を確認し、10文字以上の判断理由を記録して再開する。公開用HTMLの保存は別途承認が必要。承認は原稿・タイトル・SNS・公開準備のハッシュに紐づき、変更後は無効となる。

メール送信、実際の取材、画像の取得・加工、外部校正者の承認、WordPress登録、SNS投稿、Google Analytics取得は直接接続していない。提案・下書き・HTMLを用意し、外部への実行は人が行う。録音の文字起こしはPlaud Note等で作成して入力する。

## 情報管理

資料はブラウザのメモリとAPIリクエスト処理中のメモリにのみ保持し、自動保存、localStorage、記事本文のサーバーログは使わない。明示的に保存したJSONにはマスキング後の資料・成果物・判断記録が含まれるため、利用者が管理する。画面の消去はアプリからの参照削除であり、OS・ブラウザの物理的な完全消去を保証しない。

「機密・外部送信禁止」はサーバーでも送信拒否する。「社内限定」はメール・電話番号のマスキングを必須とし、Web検索は禁止。非公開の人名や案件名は追加のマスキング語句を指定する。自動検出は全個人情報を識別するものではない。送信前プレビューと組織の情報分類・利用許可が必要。

OpenRouterには `provider.data_collection: deny` と `provider.zdr: true` を要求し、条件に合うモデル提供元がない場合は失敗させる。これは提供元のルーティング制限であり、OpenRouter・検索サービス・ホスティング事業者の保持方針や契約をアプリから保証するものではない。組織で事業者の契約・地域・保持条件を確認する。検索は公開情報のみ、任意の追加料金機能。モデル料金はOpenRouterアカウントに発生し、APIが返した使用量・費用のみを表示する。

## 実行・ビルド

Node.js 24を推奨。依存パッケージの追加インストールは不要。

- `npm start`: http://127.0.0.1:4173 の開発用プレビュー。開発サーバーだけがローカルの仮の本人識別を付与する。外部公開しない。
- `npm test`: 根拠検証、修正重複、情報管理、認証、同一生成元、HOTL、監督承認、再開、改ざん検知の回帰確認。
- `npm run build`: Cloudflare Workers互換の `dist/server/index.js` を生成。

Vercel版はパスワードなし。Sites版は従来の本人限定アクセスと `ALLOWED_USER_EMAILS` を使用。環境設定は `.env.example` を参照。実キーをGitHubにコミットしない。GitHubのリポジトリ直下をソースの保存先とする。

## 制約と検証

根拠検証は引用IDと引用文の存在を確認するもので、事実の正確性・意味の一致を保証しない。判断ログはメモリ内のハッシュ連鎖で、署名済みの改ざん不能な監査基盤ではない。レート制限はWorkerインスタンス単位で、アカウント全体の課金上限の代替ではない。OpenRouterキー側にも支出制限を設定する。

有料モデルとの実通信は実キー設定後に確認する。自動テストの正常なモデル応答はモックである。サンプルは架空、編集ルールは実際の媒体規定ではない。実際の記事3〜10本で作業時間、修正往復数、重大な見落とし、不要な指摘を計測する。


## ダッシュボードと監督・通知（2026-10）

白・ネイビー・コーラルを基調とする3列のダッシュボードで、現在の制作の進捗、確認待ち、根拠照合、専門チームの活動を表示します。未実施の工程や架空のチームメンバー・実績を完了として表示しません。制作ナビは工程の状態から次の作業を提示し、17の専門工程が成果物を引き継ぎます。ナビ自体はルールによる監督制御であり、別のモデルによる自由なツール選択ではありません。

タスク検索、制作ブリーフのテンプレート、公開予定日、編集メモを追加しました。すべてページ内メモリのみで、再読み込みやページ終了で消えます。編集メモと予定日はAIへ送信しません。共同編集・外部カレンダー連携・公開予約には対応していません。

人の確認、取材資料、公開用データの承認、実績、処理の停止が発生すると通知センターに表示します。「ブラウザ通知を有効にする」を押してOS/ブラウザの許可を得た場合のみ、ブラウザ通知を出します。通知本文は定型文で、原稿・資料・個人名は含みません。権限が拒否された環境でも画面内の通知は利用できます。通知をクリックすると該当箇所へ移動します。通知の重複を防ぎ、原稿の修正後に再度確認が必要になった場合は新しく通知します。

**通知と制作処理はページが開いている間のみです。** ブラウザを閉じた後のバックグラウンド処理・メール・Slack・Web Pushは未実装です。通知記録は最大30件をメモリ内で保持し、「資料と成果物を消去」で消します。ブラウザ通知は利用環境やOS設定により届かない場合があり、画面内の確認待ちを併用してください。

制作ごとのAI呼び出しは再開・失敗分を含め48回までに制限し、上限で停止します。これはブラウザ上の実行制御であり、サーバー全体の課金上限・匿名利用の濫用対策を代替しません。既存のサーバーでの同時実行数・リクエスト数制限、外部送信の同意・マスキング・ZDR指定・原稿改訂時の承認失効を維持しています。APIキーは引き続きサーバー環境変数のみです。

追加検証: `node tests/dashboard-browser.mjs` と `node tests/workflow-browser.mjs`。AIとブラウザ通知はモックを使用し、有料APIの実通信は含みません。


## 編集者向けの入力・進捗画面（2026-10-03）

記事プロジェクトの最初の必須項目はテーマ・読者・目的の3つです。資料と公開後の実績は別の折りたたみ欄に分けています。業務の状態を表す「準備中」「取材待ち」「確認待ち」等は維持し、内部処理を説明するHOTL・モデル・処理回数などの表記を画面から整理しました。検索の追加料金の表示も利用画面から削除しました。検索サービスの使用料は従来どおりOpenRouterの運用費に含まれ、検索機能・運用側の費用は変更していません。

原稿レビューのガイドは淡い背景と濃い文字に変更しています。進捗は画面上部の全体の完了率と6工程のカードで示し、各作業が終わっていても人による確認が必要なら「確認待ち」を表示します。作成中の工程だけを動きのある表示にし、OSの視覚効果抑制設定を尊重します。

各文章欄にファイル読み込み・貼り付け・コピー・保存を追加しました。Word（.docx）、UTF-8のテキスト（.txt/.md）、CSV（.csv）をページ内で読み込みます。Wordは本文の段落を文章として取り込みます。画像、ヘッダー、フッター、脚注、コメントや複雑なレイアウトを取り込む機能ではありません。PDFと旧形式の.docには対応していません。サイズ上限は500KB、各欄の文字数と資料全体80,000文字の上限を維持しています。文章やWordの展開後データにも上限を適用し、認証情報や読み取れないファイルを拒否します。Wordの変換サービスは使いません。

「入力内容を保存」で企画を保存し、「企画ファイルを読み込む」で入力のみ再利用できます。送信同意・機密区分・モデル・公開承認・制作状態はファイルから読み込めず、検索の使用もファイル取り込み時にはオフにします。企画は入力用のJSON形式で保存し、利用者は画面から保存・読み込みするだけで利用できます。記事や作業の内容は読みやすいテキストでコピー・保存できます。制作記録の保存と承認後の入稿用ファイル保存は従来どおりです。

ファイルはページのメモリで処理し、読み込みだけでAIへ送信することはありません。コピー・保存した元資料は利用者が手元で管理してください。ブラウザのクリップボード読み取りが許可されない場合は入力欄へ案内し、通常の貼り付け操作を利用できます。

検証: `npm test`、`node tests/usability-browser.mjs`、`node tests/workflow-browser.mjs`、`node tests/browser.mjs`、`node tests/dashboard-browser.mjs`。有料AIの呼び出しはモックです。

## 過去記事と分類を制作に活かす

ナレッジの「記事・CSVを読み込む」から、本文TXT/MDと記事情報・分類・業界/テーママスターのCSVをまとめて読み込めます。保存済みの `angle-article-library.json` は1ファイルで再読込できます。CSVはUTF-8、本文との照合はタイトルのUnicode正規化と一意なファイル名記号の一致を使用します。広告用googletagコードは除去します。本文のない記事・公開日のない記事は補完しません。「その他」は既存分類の受け皿として補い、その他の未登録分類は候補から除外します。

検索はローカルの語句一致と頻度による順位付けです。意味検索やモデル学習ではありません。似た企画、企業名、テーマを探し、3本まで選択すると、その記事情報・冒頭600文字・分類名称が制作の `editorialContext` に入ります。送信前確認にも表示します。未選択の本文全体はAIへ送りません。取材資料のS/T・媒体ルールRとは分離し、過去記事を現在の数値や発言の出典として認めません。

企画は過去記事との差分、取材設計は数字の対象・期間・費用・例外、執筆は要点・背景・取材の説明と実績/予測の区別を指示します。これはサーバーの固定指示にも組み込み、資料内の命令では変更できません。修正稿とタイトル/SNSの数値を今回の資料と照合し、見つからない数値は人の確認まで停止します。単位を含む文字列照合なので、同じ数値の別事例・数値以外の誤りの完全検出は保証しません。承認は原稿とタイトル/SNSで別に記録し、新しい確認が必要になれば再通知します。

本番のOpenRouter出力の品質は、運営者のAPI設定後に編集者が正解付きの取材・原稿で評価してください。動作確認のモック結果や、検索で元タイトルが見つかることを、AIの正答率として扱いません。添付コーパス本体・カテゴリの実データは公開コードへ含めません。

## 制作開始が進まない場合

`/api/status` の `configured:false` は、このデプロイでサーバー用のキーや利用モデルを読み取れていない状態です。OpenRouterへ記事の処理を送る前に止まります。Vercelの対象プロジェクトで `OPENROUTER_API_KEY` を **Production** に設定し、mainの最新デプロイを **Redeploy** してください。環境変数の追加は既存デプロイへ後から反映されません。Previewだけに設定したキーは本番で使えません。`NEXT_PUBLIC_` を付けず、ユーザーの画面やソースコードにキーを入れないでください。

アプリの「接続を再確認」は、サーバーで固定の `https://openrouter.ai/api/v1/key` に接続し、キーを確認します。記事・プロンプトを送信せず、モデル生成を行いません。未設定、形式不正、認証失敗、キーの利用枠、通信障害を区別します。接続確認が成功しても、モデルのJSON形式やZDRなどの条件を満たすかは実際のモデル呼び出し時に確認されます。保護条件を弱めてリトライしません。30秒間は同じキーの確認結果を共有し、変更されたキーには別の確認を行います。

開始時に必須項目を確認し、接続状態を取得し直します。送信同意が未確認なら設定画面へ案内し、確認を適用すると依頼した制作を自動で開始します。未確認のまま閉じた場合は実行しません。接続の再確認で資料を消去せず、ページのリロードを要求しません。接続先モデルはサーバーの許可モデル一覧の先頭を使い、ユーザーがキーやモデルを指定する欄はありません。

「マイタスク」の検索は「質問を作って」「SNSの投稿案」「記事の制作を始める」などの言い方に対応します。「ここまで進める」や成果物欄の「この作業まで進める」は必要な前工程を実行し、依頼した工程まで完了すると停止します。並列確認など関連する作業はまとめて実行します。完了済みの工程は再実行せず、取材素材・原稿・公開前の判断が必要なら従来の確認で止まります。選択した作業の完了は記事全体の制作完了ではありません。公開や外部メール・SNS送信を自動で実行する機能はありません。

検証: `npm test`、`node tests/start-browser.mjs`、既存の制作・ダッシュボード・入力・Vercel相当のブラウザ検証。モデル応答とキー診断はモックでテストします。実モデルで制作が完了したことを示す検証ではありません。

## 振り返りまでの操作デモ

記事プロジェクトの「振り返りまで試す（デモ）」で、架空の企画・取材資料と固定の表示例を使い、17工程を体験できます。APIキー・外部送信の同意は不要で、外部AIへ送信しません。通常のOpenRouter制作やAIの性能評価とは区別してください。

1. 原稿の確認待ちで、確認内容を10文字以上記録して再開。
2. 実績待ちになったら「公開用データを確認」で承認する。実際の公開・投稿は行わない。
3. 入稿用ファイルを保存できることを確認し、「架空の公開実績を追加して振り返る」を押す。
4. 進捗100％と、架空のPV・問い合わせ・校正時間からの振り返りを確認。

デモは画面に常時明示し、出力にも「デモ」「架空」を付けます。保存した制作記録はdemoフラグを含みます。デモ開始は入力・成果物を置き換えるため、既存の企画があれば先に保存してください。デモ終了で入力と成果物を消去し、通常の入力と送信確認へ戻ります。ブラウザ検証：`node tests/demo-browser.mjs`（公開環境は`DEMO_TEST_URL`で指定）。

## Word・SNSなどへの受け渡し

「外部ツール」から、承認済みの成果物を確認して渡せます。WordとGoogle Docsには編集できるDOCX、Instagramにはキャプション、YouTubeにはタイトル・概要欄、XとLinkedInには投稿文を用意します。Canvaには文案CSV、WordPressには入稿HTMLを保存できます。新しい制作ではInstagram・YouTubeの文案もSNS工程で作成します。以前の成果物に該当媒体の文案がない場合は、そのボタンを無効にします。

ファイル保存・クリップボードによる受け渡しです。OAuth接続、サービスAPIへの登録、画像・動画のアップロード、自動投稿・予約投稿は実装していません。リンクには原稿や投稿文を付けず、各サービスの固定の画面だけを開きます。利用者の認証情報は取得しません。

受け渡し前に原稿とSNS文案の承認を検証し、変更後は再確認を要求します。外部送信禁止の資料と認証情報は渡せません。CSVは表計算の数式として解釈される文字列を無効化します。操作記録には媒体と受け渡し方法を残し、本文を残しません。デモ文案は画面とファイル名に明示します。

検証: `npm test`、`node tests/integrations-browser.mjs`。公開環境は`DEMO_TEST_URL`で指定。ブラウザ検証は架空のデモを使用し、AI呼び出し・外部投稿を行いません。

## 実際の生成内容を見せる

記事プロジェクトの「サンプル資料で記事を作る」は架空の入力資料をセットし、通常のOpenRouter制作を開始します。固定回答への切り替えや失敗時のデモへの代替はありません。接続確認・個人情報保護・送信同意・人の確認を通常どおり適用します。公開実績はセットせず、振り返りは実行しません。生成完了後は修正稿を表示し、作業一覧で企画・校正結果・SNS文案などを切り替えられます。従来の固定回答デモは「操作だけを試す」の中に残します。

画面には制作・確認に必要な案内を表示し、接続先名や内部形式の説明は省きます。入稿工程はHTMLコードではなく原稿の内容を表示します。資料の外部送信・個人情報の保護・停止理由・架空資料であることは引き続き明示します。

## 成果物の編集と作り直し

作業一覧で原稿・企画・見出し・SNS文案などを選び、「内容を編集」から文章を変更できます。保存すると、その内容を使う後の工程を未完了に戻し、既存の承認を取り消します。「制作の続きを進める」で後の作業を再開してください。根拠の識別情報や校正結果自体は書き換えず、原稿を直して確認し直します。入稿ファイルは原稿から作り直します。

「作り直す」は選択した工程を通常の制作サービスで再実行します。後続工程も再確認が必要です。失敗・停止した場合は前の成果物と状態を復元し、処理回数・利用記録は戻しません。固定回答の操作デモでは固定回答を再表示します。文章の編集・送信の取り扱い、認証情報の拒否、制作の回数制限、担当者による確認は維持します。会社メールでログインすると記事と編集履歴を自動保存します。未ログインではページ内だけで保持し、終了前に保存してください。

検証: `npm test`、`node tests/artifact-edits-browser.mjs`。ブラウザ検証の制作サービスは模擬応答であり、生成品質の評価ではありません。

## 実務ワークスペース

会社メールの確認コードでログインし、記事・最大30版の履歴・担当者・期限・根拠確認・投稿状況を共有します。原稿の段落だけを再生成し、Wordで修正した本文を比較して取り込めます。原稿を変更すると後続作業と承認を更新します。自動保存は変更後1.2秒、更新の競合時は上書きを止めます。閲覧者・編集者・承認者を分け、保存済み記事は90日後に削除します。承認は復元時に引き継ぎません。

本番の専用Supabase保存先は作成済みです。有効化には運営者がVercelで `SUPABASE_URL`、`SUPABASE_PUBLISHABLE_KEY`、`LOGIN_ALLOWED_EMAILS`（許可メールまたは@会社ドメイン）を設定します。データベースは `database/workspace.sql`、通知は `database/reminders.sql` を使用。公開RPCは権限を持つユーザーだけが呼び出せます。サービスロールキーは不要です。現在は許可会社メールが未指定のため、ログインとクラウド共有は未有効です。

ページを閉じていても確認依頼・締切通知を送る実装には、運営者の `RESEND_API_KEY`、確認済み送信元 `NOTIFICATION_FROM`、`CRON_SECRET` が必要です。専用データベースの2分ごとの通知ジョブと秘密値は設定済み。通知には原稿・取材内容を含めません。実メール配信には送信元設定が必要です。Supabaseの会社メール向け確認コードにはカスタムSMTPを設定し、Authテンプレートを `{{ .Token }}` にしてください。標準SMTPには宛先制限があります。

検証：`npm test`、`node tests/practical-browser.mjs`。SQLの権限・セッション失効・競合・削除を実PostgreSQL互換環境で確認します。ブラウザの模擬応答は操作検証用で、生成品質の評価ではありません。

## LPの独立プロジェクト

`landing/` にLP専用のソースとビルド・公開設定があります。アプリはリポジトリ直下、LPは `landing` をVercelのRoot Directoryとして別プロジェクトに指定します。AIキー・保存先・認証設定はLPに不要です。公開先の新規作成には現在の接続権限がなく、Vercel管理画面からLPプロジェクトを作成する必要があります。移行中は旧 `/lp.html` を維持しています。詳しくは `landing/README.md` を参照。

## 制作操作と専門担当の実行制御（2026-10-04）
必須入力の直後に制作開始を配置し、スマートフォンでは次の操作を画面下に固定します。サンプル・企画ファイル・媒体設定は折りたたみ、生成後の編集、作り直し、ファイル操作をまとめています。記事のクラウド保存とファイルのダウンロードは表示を区別しています。

専門担当へ渡す入力項目と前工程の結果を `dist/agent-input.js` で定義し、ブラウザとサーバーの両方で適用します。調査に文字起こしや実績を渡さず、SNS担当には記事と見出しを渡します。記事本文に含まれる情報まで取り除くものではありません。機密区分・同意・認証情報検出・個人情報マスキング・学習拒否/ZDR指定は別の制御として維持します。接続先のリダイレクトは拒否します。

明示的な一時接続障害（provider_unavailable の502/503、upstream_unavailable）のみ、同じ担当を1秒後に1回再試行します。認証・権限・情報保護・利用上限・タイムアウト・不正な出力は自動再試行しません。再試行も48回の制作上限に含み、停止操作で待機を中断します。再試行は実行記録に残り、追加リクエストが発生するため料金削減を保証しません。サーバー全体の課金上限や永続的なバックグラウンド実行は別途必要です。

## 画面のエラー表示と運営者向けコード（2026-10-09）

利用者向けの表示は、技術用語を使わずに「何が起きたか」「どうすればよいか」を伝えます。運営者の対応が必要なものには「（コード：S04）」のようなコードを付けます。利用者から問い合わせを受けたら、次の表で原因を確認してください。サーバーのログにも同じ原因が `code` として記録されます。

| コード | 原因（ログの `code`） | 運営者の対応 |
|---|---|---|
| S01 | `missing_key` / `openrouter_key_required`：OpenRouterのAPIキーが未設定 | Vercelの環境変数 `OPENROUTER_API_KEY` を設定し、Redeploy |
| S02 | `invalid_key`：APIキーの形式が違う、または無効 | OpenRouterで有効なキーを発行し直して設定 |
| S03 | `model_not_configured`：使えるモデルが設定されていない | `ALLOWED_MODELS` を確認 |
| S04 | `credit_required` / `provider_credit_required`：残高またはキーの利用上限が不足（ログの `affordableTokens` は残りでまかなえる出力量） | OpenRouterでクレジットを追加するか、APIキーの利用上限を引き上げる |
| S05 | `provider_auth_failed`：OpenRouterがキーを受け付けない | キーの有効・無効、権限を確認 |
| S06 | `provider_policy_unavailable`：データを保持しない条件（ZDR等）を満たす提供元がない | `ALLOWED_MODELS` を条件を満たすモデルに変更 |
| S07 | `provider_model_unavailable`：指定モデルが利用できない | 時間をおいて再確認するか、モデルを変更 |
| S08 | `provider_route_unavailable`：モデルの提供元に接続できない | 時間をおいて再確認するか、モデルを変更 |
| S09 | `provider_access_denied`：OpenRouter側でアクセスが拒否された | OpenRouterの権限・プライバシー設定を確認 |
| S10 | `provider_request_rejected`：リクエストが受け付けられない | モデル設定と入力量を確認 |
